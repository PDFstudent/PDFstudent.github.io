DualVLN 微调：专家像素标签、冻结主干与可训练条件

解释专家目标如何投影为像素监督，以及 System2 冻结后为何仍参与计算和梯度传递。

训练数据验证

已经提供了专家目标像素，System2 为什么还要运行？这个问题来自对数据预处理的误解：保存目标像素，并不意味着已经把 System2 的全部作用预先算完。原讨论描述的是一条特定的局部微调路径：用专家标签约束目标，同时保留视觉语言网络产生条件表示的过程。

专家目标来自几何，而非模型提前作答

从未来路线到当前图像

原回答描述的数据处理先回放专家动作，保存 RGB、深度与位姿，再选择未来可见的路线点，把它投影到当前相机图像。模型资产可用于 tokenizer、图像预处理配置和训练读取检查；仅仅挂载了权重文件，不能证明预处理运行了 System2 推理。

下面是对该过程的通用几何解释，不是对未读源码的逐行复述。设世界点为 P_w，T_cw 是世界到相机的变换，K 是相机内参。先求 P_c=T_cw P_w，再将 K P_c 按深度归一化。在相机坐标采用正 Z 为前方时：

u = fx * Xc / Zc + cx
v = fy * Yc / Zc + cy

fx、fy 是像素尺度焦距，cx、cy 是主点。Zc 必须在相机前方且非零，像素应落在有效成像范围。不同仿真器坐标约定可能不同，需要先做坐标轴转换，不能直接套公式。点在画面内也不等于无遮挡；“未来可见目标”还要满足遮挡、深度、路径进度及标签规则。

为什么要把这些结果保存

保存图像、像素目标与未来轨迹，是为了分离昂贵的仿真采集和反复训练，并固定标签版本。即使之后解冻 System2，原始观测与专家标签仍可能有价值。反过来，先用冻结 System2 生成目标再训练 System1，是另一种标签生成方案：预测目标可能与专家轨迹不一致，需要明确噪声处理和条件匹配，不能把它当作同一数据集。

像素坐标不是慢系统的全部输出

显式目标与隐式规划条件

两个像素坐标能描述“朝哪里看”，却难以完整表达“走向门口”与“经过门口继续走”的差别。原讨论所述 DualVLN 路径还读取 latent query 位置的隐藏状态，经连接模块传给轨迹生成器：

图像 + 指令 + 专家目标像素
        ↓
视觉语言主干
        ↓
latent query 隐藏状态 → cond_projector
        ↓
System1 当前视觉特征 + 规划条件 → 局部轨迹

原回答报告使用 4 个 query 位置；这是当时讨论实现的参数，不能推广成所有版本的固定接口。查询向量、投影层的形状、位置和训练开关，都应随具体模型配置核对。

专家目标替代的是训练阶段的目标选择，不是整个条件计算。闭环中没有专家提供答案，需要恢复模型生成目标与条件的过程。因此，专家条件下轨迹损失下降，不自动保证模型自选目标时仍然有效；提前 STOP 等高层问题也不一定能由低层微调修复。

冻结权重不等于取消前向或梯度链

需要梯度的输入可能穿过冻结模块

令冻结网络为 F_θ，可训练查询为 q_φ，下游轨迹头为 G_ψ，损失写成 L(G_ψ(F_θ(x,q_φ)),y)。冻结 θ 只是不更新这组参数，φ 仍可能需要：

dL/dφ = dL/dF · dF/dq · dq/dφ

这条链要求保留对查询输入的求导能力。无条件把整个冻结网络放进 no_grad()，可能切断查询学习；反之，若模块的输入和参数都不需梯度，关闭该段记录才可能是合适优化。应以 requires_grad、实际非空梯度和一次更新后的参数变化核验，不能只看模块名称。

视觉缓存的有效边界

特征缓存可写为 z=E_θ(P(x))：编码器 θ、预处理 P 和输入 x 一致时才可能重用。同一张图经过会更新的 System1 RGB 编码器，输出会随训练改变，固定缓存会把这条训练路径切断。

冻结 System2 的图像编码阶段在满足确定性和接口条件时可能独立缓存；但整个条件表示还可能依赖指令、专家像素、图像顺序和可训练 query，不能仅凭“主干冻结”缓存全部隐藏状态。数据增强变化、裁剪、分辨率、模型版本及训练/评测模式，也应纳入缓存身份。

结论与证据边界

本篇来自已读原问题和回答，对其中的实现解释进行归纳；本轮没有重新检查上游源码、训练模型或运行机器人。上述公式是说明机制的通用推导，4 个 query 与模块名属于历史回答报告的实现细节。实际验收需同时检查标签几何、条件生成、训练参数和部署时条件分布。相关架构见 InternVLA 双系统，实际更新的判据见 微调验证。

后续澄清：数据里有深度，模型却可能不使用

标签生成、数据读取与模型消费是三个环节

11 月 4 日问答进一步区分了专家地图、场景、指令与动作回放所产生的 RGB、深度、位姿、像素目标和未来轨迹。深度可用于遮挡检查和标签构造；训练读取器可能仍加载该字段；所讨论的 nextdit_async 模型分支却不一定把它用于轨迹预测。早先把这些环节合称“模型使用深度”的说法不够准确，应按实际消费位置判定。

变量名中出现 depths 或类似缩写，不是计算依赖的证据。反过来，确认模型不消费深度，也不能立即删除全部深度文件：现有读取器或标签处理可能仍依赖它，需要先适配入口并验证读取。这是原讨论报告的调用链区别，本轮没有重新访问或测试该项目源码。

保存格式不能替代几何和字段协议

原讨论还说明，读取训练样本时需要把世界轨迹转换到观察时刻的局部系，并按明确时间尺度重采样。视频、Parquet 与 metadata 的组织方式可以便于保存，但“类似 LeRobot”不能等同于符合某个标准数据集规范。字段类型、形状、帧率、索引、无效点与坐标约定仍需逐项验证；录包来源的对应问题见 MCAP 训练数据契约。

潜变量没有真值时，四个 query 靠什么学习

显式目标监督与轨迹监督分阶段作用

后续讨论澄清：训练数据提供轨迹或目标信息，并不直接提供“四个潜变量的正确答案”。第一阶段可对 System 2 的像素目标、转向、LOOKDOWN、STOP 等输出做监督微调；第二阶段将四个可学习 query 放在像素目标文本之后，经 System 2 得到条件表示 Z'=f_S2(X,Z)，再交给 System 1 的图像融合与轨迹生成模块。原讨论所指配置输出 32 个轨迹点，这不是所有实现必须采用的长度。

这里 Z 是跨样本共享的可学习输入，Z' 则依赖当前图像、指令与上下文。不能分别给四个 query 强行指定“方向、速度、距离、置信度”等语义。冻结 VLM 参数也不等于切断梯度：若计算图保留，轨迹损失仍可穿过冻结网络更新 query 与其他可训练模块；若错误地整体放进 no_grad，这条路径就会中断。

Flow matching 提供的是轨迹学习信号

设真实轨迹为 X₀，噪声为 ε，连续流时间为 u，训练中可构造 X_u=α_u X₀+σ_u ε，目标速度为 dX_u/du=α'_u X₀+σ'_u ε。网络根据带噪轨迹、时间、条件表示 Z' 和视觉特征 F 预测该速度，损失可写成：

L_flow = E[ || fθ(X_u, u, Z', F) − (α'_u X₀ + σ'_u ε) ||² ]

系数的方向与端点约定必须和实现一致。这是通用推导，用来解释轨迹损失怎样训练条件表示，不意味着本次重新核实了某私有训练脚本的全部细节。反向传播把“什么条件有助于生成正确轨迹”的信号送给 query、投影器、视觉融合和轨迹网络；不需要人为构造 latent 标签。

为什么显式像素目标仍有价值

多个相似门口的例子说明：显式目标先表达“去哪个位置”，后面的 query 可以在因果注意力中读取这个目标，再表达执行所需的连续条件。训练时输入真值像素文本、推理时输入模型预测目标，还会产生训练与推理分布差异，应在实验中核查。去掉像素目标并非数学上不能训练，但“更快收敛、更稳定或更泛化”都需要消融，而不是靠模块图证明。

若像素目标正确而轨迹错误，问题可能在轨迹头，也可能在视觉特征、坐标约定、时序或下游控制器。该现象只能缩小排查范围，不能单凭一次结果判定 System 1 有错。本节保留原讨论的机制解释和待验证判断，不把它写成完成过的训练实验。
