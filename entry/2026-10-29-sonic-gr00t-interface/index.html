GR00T 怎样通过 SONIC 控制全身动作

把 64 维运动表示、78 维动作块、29 维身体控制与两种时间频率分开，解释示教和部署的匹配条件。

GR00TSONICmotion tokenaction chunk

“GR00T 已经输出动作，为什么还需要 SONIC？”问题出在动作的语义没有说清。2026 年 10 月 26 日与 28 日的原讨论指出：策略层动作可以是末端目标、关节目标或运动隐表示，只有与机器人形态配置匹配后才能确定怎样执行。下面聚焦讨论中的 Unitree G1 + SONIC 路线。

从三类输入到两条输出通道

GR00T 和 SONIC 各自读取什么

GR00T 从图像、语言与机器人状态预测未来动作块。SONIC 的控制解码器读取目标运动 token 以及实时本体状态；本体状态来自关节与惯性测量等反馈。图像和语言由上层处理，不应直接塞进标准 SONIC 控制解码器。

参考动作路线可以先经过 SONIC 编码器；当微调后的 GR00T 直接预测相同动作空间的 token 时，可跳过这些动作编码器。

RGB + 指令 + 状态 → GR00T → motion token序列 → SONIC + 实时本体反馈
                         └→ 左右手动作              ↓
                                             身体关节目标

64、78 和 29 为什么不是互相矛盾的维度

原讨论中的 UNITREE_G1_SONIC 配置每个时间步含 64 维身体运动 token、7 维左手与 7 维右手，合计 78 维。若动作块长度为 40，则不含 batch 的输出形状为 [40,78]。token 进入 SONIC 后得到 29 个身体关节的控制输出，手指使用另一个通道。

# 接口说明示例，不是可直接驱动硬件的完整实现
motion = action_chunk[:, :64]
left_hand = action_chunk[:, 64:71]
right_hand = action_chunk[:, 71:78]

64 维 token 不是 64 个关节，也不能认定其中某一维专门对应某条腿。它是联合学到的分布式表示。实际数组是否归一化、是否量化、关节顺序和缩放，必须与训练数据、检查点和部署配置一致。原讨论引用的工作流

为什么同一 token 能产生不同控制输出

身体反馈形成真正的控制闭环

控制关系可以写成 a_t = D_control(z_t, s_proprio_t)。z_t 表示目标运动；s_proprio_t 表示当前及历史本体状态；a_t 是策略的身体动作输出。机器人略微倾斜或关节存在偏差时，即使 z_t 相同，解码器也需要采取不同的修正。

所以 SONIC 不是静态姿势字典，更不是对语言动作进行字符串翻译。动作随后经过与机器人一致的目标映射及伺服控制；底层 PD 示例与运动训练机制见 SONIC 与 SuperMimic。

低频预测与高频执行

原讨论引用的部署默认值是 GR00T 约 2.5 Hz 预测动作块，动作发布与 SONIC 控制约 50 Hz。40 个点以 50 Hz 排列对应约 0.8 秒的预测时域；它不代表系统必然开环执行完 0.8 秒才观察一次。

每 20 ms，低层可以利用最新身体反馈执行控制；上层按自己的推理节奏更新动作块。新旧块的对齐、缓存、时间戳和过期处理仍是部署程序的责任，较长动作块也不保证较快的视觉响应。原讨论提到 Python 推理客户端通过 ZMQ 连接策略服务与 SONIC C++ 程序，但未在本机运行该链路。原讨论引用的推理接口

示教数据如何让两套模型衔接

记录上层要预测的动作空间

示教时人通过遥操作发出动作意图，SONIC 控制身体，同时记录图像、语言、状态、对应 motion token 和手部动作。GR00T 学习从观测预测这些标签；部署时用 GR00T 替代人的输入，继续使用匹配的低层控制器。

仅有 SONIC 的人体动作捕捉数据，并不自动等于 GR00T 的视觉语言训练数据。前者训练怎么稳定运动，后者还要知道在当前视觉任务中何时、向哪里运动。不同 SONIC 检查点的隐空间可能不同，替换检查点不能假定旧 token 仍表达同一运动。

基础权重、后训练与任务能力

原讨论明确区分基础模型支持某个机器人标签，与可以零样本完成目标任务。UNITREE_G1_SONIC 被讨论为需要对应示教和后训练的配置；不能把基础权重加载成功称为已经具备通用全身操作能力。

另一路接口可让上层输出头部与双手目标位姿及导航指令，通过规划器和混合编码器生成 token。这与直接预测 token 是不同路线，不能把两套输入要求拼成一个必需字段清单。

结论与边界

什么时候需要 SONIC

只有动作空间定义为 SONIC motion token 的策略，才需要匹配的 SONIC 解码器。普通机械臂可以执行末端或关节目标；轮式平台可以使用自己的轨迹和速度控制器，不必引入人形控制器。

全身移动操作也不同于跨房间 VLN：平衡、迈步和伸手并不能替代路线记忆、目标搜索与停止判断。本文结论来自原讨论及其引用资料，未做 G1 实机联调；50 Hz、40 步、78 维等数字均属于所讨论配置，部署前应核对版本和检查点。
