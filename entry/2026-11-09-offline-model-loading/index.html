离线模型已缓存，为什么 tokenizer 仍然访问网络

从子进程退出回溯到 tokenizer 的仓库类型查询，区分缓存文件、模型身份和离线加载契约。

技术复盘验证边界

权重已经下载、离线模式已经开启，策略服务仍在启动时退出。问题不一定在权重读取：processor 和 tokenizer 的初始化也可能根据仓库 ID 查询模型元信息。11 月 9 日的原讨论先看到父进程报告策略服务退出，随后提供的日志才暴露真正的末端异常。

从父进程错误回到第一条致命异常

警告与终止原因分开解释

父进程只知道子进程没有启动成功，不能据此认定显存不足。实际提供的日志沿着 Qwen3VLProcessor → tokenizer → _patch_mistral_regex → is_base_mistral → model_info 最后到达 OfflineModeIsEnabled。前面的 FlashAttention dtype 警告值得另查，但它不是该堆栈显示的终止位置。本次归档读取了所附日志，没有重新启动模型服务。

这条链解释了看似矛盾的现象：本地存在 tokenizer 文件，不代表所有加载辅助逻辑都只用本地文件。一个加载调用可以先命中缓存，再因模型类型识别进入 Hub 元信息请求。

仓库 ID 和本地快照目录为什么行为不同

固定版本的源码证据

在 Transformers v4.57.3 的 tokenizer 基类中，Mistral 正则修补路径会判断输入是不是本地目录；对远端仓库标识，相关分支可能调用 model_info 查询模型类型。使用本地路径能让该判断走本地分支。这是特定版本的源码解释，不是所有 Transformers 版本都会这样失败的承诺。版本源码

一种可复现的离线策略是先把仓库身份解析为已缓存快照，再把本地目录交给 processor：

from huggingface_hub import snapshot_download
from transformers import AutoProcessor

snapshot = snapshot_download(
    repo_id=model_id,
    revision=revision,
    cache_dir=cache_dir,
    local_files_only=True,
)
processor = AutoProcessor.from_pretrained(
    snapshot,
    local_files_only=True,
)

model_id 指定仓库，revision 固定版本，cache_dir 选择缓存，local_files_only=True 禁止用下载弥补缺失。若该版本快照没有缓存，第一步应该明确失败，而非临时改用其他版本。这个片段说明接口语义；完整运行还要检查所需文件和自定义组件是否齐全。

缓存不是预先算好的视觉特征

Cosmos 等基础模型缓存存的是配置、tokenizer、processor 与权重等资产。每张新图像仍要经过在线前向计算。构建基础骨干后再加载 GR00T checkpoint，是实例化结构并恢复最终参数的过程，不等于同时运行两个彼此独立的决策策略。最终采用哪些参数，应以加载顺序、缺失键和覆盖键为准。

修复加载之后，验证到哪一步才算完成

仅执行 processor 初始化可以证明元信息查询问题绕过了，不能证明策略前向、环境动作或任务成功。应逐层检查 processor、权重恢复、单批前向、环境闭环和任务指标，并记录每一步使用的版本。

后续原讨论报告了完整策略闭环和短训练检查，详见 GR00T 与 LIBERO 验证。它们是原回答中的运行报告；本次知识库任务只验证文章生成和发布。模型加载成功仍不能证明训练或泛化指标达到目标。
