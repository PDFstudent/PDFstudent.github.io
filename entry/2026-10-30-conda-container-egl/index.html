Conda 迁移到容器后：为什么 CUDA 可用而 EGL 渲染失败

区分环境归档、容器系统依赖和运行时驱动，通过厂商库与 GLVND 注册定位无窗口渲染失败，并逐层验证迁移结果。

Conda容器CUDAEGLHabitat

环境已经能导入 PyTorch 和 Habitat，GPU 张量计算也成功，但无窗口仿真仍提示找不到与 CUDA 设备对应的 EGL 设备。这并不矛盾：计算与图形经过不同的运行时组件，而“打包好了 Python 环境”也没有覆盖容器运行的全部依赖。

原讨论从环境迁移进入实际渲染排障。本文抽取其中独立可复用的依赖关系、诊断过程与证据边界；所有平台操作、内部镜像地址和部署信息均省略。

Conda 环境归档离镜像还差哪几层

环境归档保存什么

conda-pack 的产物是环境归档。它可以用于异路径迁移及路径修复，但不会自动变成包含基础操作系统的容器镜像，也不能包办宿主机 GPU 驱动。环境外的 editable 源码尤其容易遗漏：Python 包入口存在，并不意味着被引用的源码已随归档带走。

可以把依赖关系写成：

基础 Linux 用户空间与系统库
  + Python/Conda 环境
  + 固定版本的配套源码
  + 安装、路径修复与启动配置
  = 容器内可复用运行环境

运行时还需要宿主机驱动、GPU设备和相应驱动组件

归档哈希和文件大小能证明传输完整性，但不能证明 GPU 或图形兼容。网页上传入口的限制也不等于后端容量；大文件传输要选择支持分片的入口，完成后仍应核对内容完整性。

本地构建和远端构建的共同要求

Dockerfile 可以在本地或远端构建，构建地点不是可复现性的判据。应固定基础镜像身份、依赖版本、源码提交及安装步骤。交互式安装后保存镜像可以保留当前环境，但要另外记录它如何形成，否则仅凭快照难以重建和解释差异。

迁移检查要使用明确的解释器，并查看包实际导入位置。基础环境继承的 PYTHONPATH、PYTHONHOME、用户 site 包或 pip 约束可能污染另一套环境；应按需要隔离这些变量，而不是看到 import 成功就认定加载了目标版本。

三个成功信号分别证明什么

把测试拆成独立层次

检查能证明尚不能证明
核心包导入解释器能找到并加载相关模块GPU 张量实际可执行
一次 CUDA 张量运算该运算经过可用计算后端EGL/OpenGL 图形设备可用
场景 RGB 渲染图形上下文及场景渲染链路工作物理仿真、机器人运动和训练轨迹正确

NVIDIA 文档分别把 compute、utility、graphics 对应到计算、管理工具和图形能力。因此 nvidia-smi 成功或 CUDA 运算成功，都不能代替 EGL 检查。驱动能力是在容器运行配置中生效的；修改已运行 shell 的文字变量不保证补上创建时缺失的组件。NVIDIA 容器驱动能力说明

库可加载，为什么厂商实现仍没有被找到

原讨论中的证据链

原讨论提供的脱敏技术输出依次表明：场景校验通过、CUDA 张量运算通过、EGL 初始化失败；进一步检查发现通用 EGL 库和 NVIDIA EGL/GLX 库可以加载，但厂商注册文件只列出 Mesa。诊断因此缩小为“后端库存在，厂商发现链路不完整”，没有直接把问题归咎于模型或场景。

GLVND 是厂商中立的分发层。能加载 libEGL.so.1 只说明前端可用，仍需要发现并加载对应厂商实现。本轮查看上游 LoadVendors 代码：显式文件列表优先于目录扫描；未提供目录变量时使用编译配置的默认目录。这解释了为什么一个存在的后端库可能没有被选入。GLVND 厂商加载源码

针对缺少注册的最小修复

在确认 NVIDIA 后端库确实可加载、ABI 与运行环境兼容之后，厂商文件的核心内容是：

{
  "file_format_version": "1.0.0",
  "ICD": {
    "library_path": "libEGL_nvidia.so.0"
  }
}

这里 library_path 指向已经存在的厂商库。文件应放在该 GLVND 构建实际扫描的位置；不要把某台机器上的目录当成所有环境的保证。可先用 __EGL_VENDOR_LIBRARY_FILENAMES 指向这一测试文件，验证后再移除该覆盖以及 __EGL_VENDOR_LIBRARY_DIRS，确认默认发现过程也正常。

这是一个有前提的修复：驱动库不存在、设备没注入、库版本不兼容或设备索引映射错误时，新增 JSON 都不能替代根因处理。不要为此直接破坏其他厂商注册或删除 Mesa 库。

如何确认修复范围而不过度宣称成功

历史观察与当前检查分开

原讨论中的用户输出显示：显式指定厂商后渲染成功；取消覆盖变量后再次成功，图像数组为 480×640×3。测试关闭了物理仿真，并明确没有验证轨迹采集。这些是历史对话中的实际输出，本轮归档未重新运行该 GPU 环境。

图像检查可以按以下条件组织，示例不含具体场景和本机路径：

assert rgb.shape == (480, 640, 3)
assert np.isfinite(rgb).all()
assert float(rgb.std()) > 0

尺寸和有限值帮助发现输出格式问题，非纯色检查能捕捉部分异常，但都不能代替人工确认场景是否正确。随后还要分别测试物理初始化、动作步进、机器人与目标位移、视频动作同步及持久化输出。

后续仍待验证的内容

迁移成功应以新环境中的独立检查为准。一次图片成功无法保证完整 episode 有效，也不能证明模型训练质量；环境快照中的修复是否能在重新创建的容器里重现，需要再次验证。相关数据与仿真证据层次见 OmTrackVLA 数据训练专题。
