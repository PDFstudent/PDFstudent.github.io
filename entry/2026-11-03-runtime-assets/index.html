容器安装、镜像快照与数据版本：运行环境究竟保存了什么

串起安装、快照、挂载卷、版本化数据和 GPU 渲染验证，区分文件存在与运行证据。

训练数据验证

在运行容器的终端安装完依赖，随后又构建一个镜像，看起来像做了两次环境安装。原问题的关键在于三种对象不同：启动容器的原始镜像、容器运行时改变的文件系统，以及保存这些改变后生成的新镜像。

安装改变容器，快照保留状态，构建定义复用

一条 FROM 不会重放终端历史

普通容器内安装会写入可写层，原始基础镜像不会因此改变。平台若提供保存容器文件系统的快照功能，新快照可以包含已安装的软件；再通过 FROM 引用该快照，就是继承已有内容，不是重新执行此前的安装命令。

通用示意为：基础镜像 → 运行容器 → 安装与检查 → 保存快照 → 发布可引用版本 → 新容器复用。快照适合保存已验证状态，但它本身不说明状态如何产生。要可重建，还应保留依赖锁定、安装步骤、基础版本与验证方法；标签可能被重新指向，严格复现应记录内容身份。

挂载内容不能靠保存环境来保全

卷或外部数据挂载的生命周期与容器层不同。常见容器快照不包含挂载卷内容，具体平台若支持其他保存机制也应单独核对。不能因为训练进程能读取数据，就认为数据已经进入环境镜像。

依赖环境、代码、数据、预训练权重和输出结果各有身份。把它们分开管理，可避免环境升级悄悄替换实验输入；保存后的镜像还需启动全新容器验证，避免测试依赖旧容器残留文件或未声明挂载。

数据卷与数据集版本解决不同问题

可变工作存储与实验输入身份

数据卷适合持续写入、中间处理和共享缓存，但同一路径的字节可以改变。数据集版本用于给一批输入建立稳定引用；版本名称不自动保证不可变，仍要核对平台语义和实际文件哈希。

例如采集得到的原始记录先进入工作存储，经完整性、时间同步、质量筛选后形成训练版本。训练记录应同时指向源数据身份、处理代码及参数，才能解释转换后的样本从哪里来。持久化也不代表永久保留，还取决于保留策略和访问权限。

MCAP 与 LeRobot 不是简单换后缀

MCAP 可承载相机、状态、控制命令与时间戳等消息；LeRobot 格式更接近按 episode 组织的训练数据。转换需要确定观测与动作的时间对齐、坐标系、单位、动作空间、视频引用和缺失帧处理。已经是 LeRobot 格式，也不能省略模型输入字段和标签含义检查。

原始数据和转换结果应分开保存并保持对应关系。发现时间偏移或动作单位错误时，能从原始记录重新处理，不必重新采集。机器人也不必直接挂载训练平台数据卷；可通过采集服务或对象存储导入，具体接入方法需要实际验证。

“GPU 可用”至少有四个独立层次

算子与图形栈分别测试

库成功导入只证明一部分依赖关系；CUDA 张量计算进一步证明所选算子能在设备上执行。它不证明 EGL/OpenGL 初始化和场景渲染可用，也不证明物理仿真或模型推理能完成。

原讨论先检查运行依赖和实际 CUDA 计算，再构造 RGB 相机、加载场景、设置位姿、读取图像。通用图像检查应包括形状、类型、有限数值、内容变化与落盘可读性。像素标准差大于某个阈值可排除部分纯色失败，但阈值只是启发式，不能单独证明相机位置或场景正确。

只为已使用能力解释警告

缺少语义标注可能不影响只请求 RGB 的测试，却会影响依赖语义观测的任务。验证报告应明确 rendering_tested、physics_tested、model_inference_tested 等能力范围。RGB 渲染通过后，仍需加载模型、执行动作并核对闭环终态。

缺少代码挂载是另一种独立失败：即使镜像与数据都正确，启动入口可能根本不存在。通用 shell 写法 ${CODE_ROOT:?missing code input} 可以在变量缺失时提前失败，但还要检查文件可读、实际版本以及所需资源存在。

结论与证据边界

本篇提取原讨论中的通用运行机制，省略内部平台、地址、路径与资源配置。原回合包含依赖检查和 RGB 渲染输出，本轮只读取这些历史证据，没有重新执行同类测试。环境复用的最终证据应来自新容器和明确输入，而非旧会话中的一个成功标志。

离线包完整，为什么容器仍可能跑不通

缓存引用、解包峰值与持久化边界

后续讨论关注离线依赖的交付形态。模型缓存中的 snapshots、blobs 与 revision 引用可能互相依赖；只复制一个看似完整的目录而遗漏实际 blob，会在离线加载时失败。应验证引用目标存在、文件校验值一致，排除认证文件。缓存压缩包只是模型资源包，不等于包含系统库和运行环境的 Docker 镜像。

平台把上传资源归在“数据集”栏目，也不代表内容会用于训练：模型依赖、配置与离线包仍应按运行资产管理。只读挂载可作为输入源，解压和编译则要使用可写空间。磁盘需求要计算压缩包、解压产物、wheel/编译缓存和环境可能同时存在的峰值；df 显示底层文件系统容量，不能替代用户配额、容器可写层或平台资源限制的核查。

CUDA、渲染和模型闭环要分别验收

MUJOCO_GL=egl 与 PYOPENGL_PLATFORM=egl 只是选择后端，不能凭空提供缺失的 EGL 驱动或动态库。CUDA 导入、BF16 矩阵运算或反向传播通过，只证明对应计算路径可用；它不证明渲染上下文能建立，更不证明策略权重、观测预处理、动作接口和环境闭环正确。

验证可以沿依赖逐层推进：先检查库加载与基本计算，再做实际策略前向，再创建渲染环境并保存可检查的图像，最后跑闭环回合并测试保存后重启。每层保留具体输入和产物，避免把“包已安装”“镜像已保存”和“任务成功”写成同一状态。后续原回答报告了基础环境验证的进展，但并未提供完整策略与渲染闭环完成证据；本次也没有执行这些模型实验。

重启后占用骤降，先确认环境是否还存在

重启旧容器与从镜像创建新容器不同

后续讨论中，安装环境消失而恢复材料仍然存在，随后确认实例曾终止并重新启动。这个现象支持“运行环境与持久化材料位于不同保存范围”的解释，不能由界面上的相同名称推断原可写层仍在，也不能推广成所有容器重启都会清空安装。

排查时先分别核验环境入口、解释器、必要依赖和外部挂载。若环境仍在，先做运行验证；若环境不在而恢复材料还在，可以复用材料重建；若两者都不在，则需先确认实例和挂载身份，而不是立即重复安装。通用 Docker 的 commit 不包含挂载卷中的数据，见官方说明；平台自有快照是否另行保存卷，需要独立确认。

隐藏错误会把“没有统计到”伪装成“很小”

原讨论中，磁盘统计只输出少量缓存信息，却没有目标环境目录。当命令使用 2>/dev/null 时，目录不存在的报错被丢弃，后续排序仍可能正常输出。此时小数字不是精简效果的证据。比较前后体积，必须先保证测量对象相同且存在，并保留 stderr 和退出状态。

一个不绑定本机路径的检查示意是：

# RUNTIME_DIR 由当前环境明确设置，不使用猜测值。
: "${RUNTIME_DIR:?set runtime directory first}"
test -d "$RUNTIME_DIR" || exit 1
du -sh -- "$RUNTIME_DIR" || exit 1

这只验证目录存在及其统计结果，不验证依赖完整，也不保证统计值等于平台镜像保存计费或限额口径。若用管道保存日志，需要同时关注前序命令失败是否被末端工具的成功状态掩盖。

镜像过大时，怎样精简而不丢失必要能力

分清临时占用、运行依赖与保存口径

原问题包含镜像保存因大小限制失败。可复用的处理顺序是先确认限制统计什么，再区分安装临时目录、下载缓存、实际运行依赖和外部挂载；特定平台限额不作为通用参数。清理临时材料只能解释临时占用变化，不能证明环境本体变小；镜像层、压缩方式与平台封装也可能使最终保存大小不同于一个目录的 du 结果。

容量预算应覆盖即将加入的仿真依赖，而不只让当前环境勉强低于阈值。已验证的阶段环境可以作为恢复节点，但保存任务显示成功之后，仍应使用其生成的明确镜像版本创建新实例，并验证挂载和运行入口。磁盘够用、保存受理、保存成功和新实例可运行，是四个独立条件。

可选后端是否能去掉，要由执行路径和验证共同决定

原回答检查当前 PyTorch 入口后，提出省去未使用的 TensorRT 依赖。这个判断只针对所读执行路径，不能推广成 GR00T 或所有推理环境都不需要 TensorRT。搜索不到直接 import 只能提供线索，仍需检查间接调用、插件加载、包声明依赖及其他入口。

精简后可先做依赖一致性检查，再测试实际能力。pip check 文档说明它检查已安装包的依赖兼容性；通过不代表动态库、CUDA 算子、图形上下文或策略前向都能运行。相反，出现声明依赖缺失时也不能仅凭一次 import 成功就忽略，应弄清支持的安装组合及受影响功能。

截止本次归档日，原回答只报告精简脚本已通过静态检查，实际安装、体积达标和镜像保存尚待确认。先前环境的验证结果不能自动转移给后来的精简方案。本文没有执行环境修改或模型实验，也没有把下一自然日的未归档回答提前用作结论。
