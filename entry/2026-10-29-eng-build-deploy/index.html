构建产物、完整部署与回滚

解释编译成功为何仍可能无法部署，检查产物边界、ABI、空间峰值、版本切换与实际回滚能力。

构建Conan交叉编译部署

源码编译成功，复制到机器人却找不到包、动态库或资源，通常要检查的不只是“有没有编出来”。SDK、应用安装目录和完整运行包的边界不同；多包共享安装前缀时，单独覆盖一个目录也未必完成依赖升级。

这里按产物身份、架构与 ABI、完整性、激活和回滚五步解释部署。目标是让设备运行一个可追溯的完整版本，失败时能回到已知版本。

编译成功后，手里的目录是否真的是完整运行包

先识别产物用途，再决定怎样复制。目录看起来相似，不代表依赖边界相同。

项目依赖边界

接口定义、应用代码、系统集成包和设备运行时可能分别构建，却在部署根目录中交叉安装文件。

单应用热替换只适合目录边界清晰的组件。接口包的动态库、共享资源和包索引分散在多个位置，必须作为完整依赖图部署。

编译只生成目标文件。部署还需要目录布局、环境脚本、动态库、资源文件、包索引和版本清单。

SDK 压缩包、源码 install 目录和完整运行包用途不同，不能因为目录结构相似就直接覆盖正式根目录。

Merged install

Merged 模式把多个包安装到共同前缀，便于运行，但文件所有权分散。升级单个基础接口时，难以安全删除旧文件。

因此接口 ABI 变化应重新组装完整集成包，而不是把某个 share 子目录覆盖进去。

源码相同，为什么换工具链后仍可能运行失败

编译器、目标系统和依赖共同决定二进制兼容性。仅核对 CPU 架构不足以确认运行环境一致。

交叉编译

检查目标架构、系统库版本、动态加载器和工具链。部署前使用二进制检查和动态库检查确认产物与设备匹配。

在设备上直接编译可以避免交叉工具链差异，但会消耗存储和时间。必须明确依赖来自系统还是 Conan，避免与正式运行库混合。

Conan 工具链

工具链文件定义编译器、sysroot、搜索前缀、构建类型和依赖路径。更换工具链可能改变 ABI、标准库和查找顺序，即使源码不变也会产生运行差异。

怎样估计部署峰值，并避免运行时半覆盖

部署不是一次复制，还包含临时解压、新旧版本并存和切换过程。空间预算必须覆盖峰值。

空间峰值

部署时可能同时存在压缩包、临时解压目录、当前正式目录和备份。需要计算峰值，而不是只看最终目录大小。

同时检查 inode，特别是 ROS 安装树包含大量小文件。

先写入独立版本目录，完成校验后再切换当前版本指针。不要边运行边覆盖正式文件。

文件完整性

传输后比较缺失文件、大小或校验值。少数不可读缓存目录导致传输返回失败，不代表业务文件全部缺失，也不能直接忽略错误。

一个空间峰值与切换边界的例子

假设压缩包 2 GB、解压后的新版本 5 GB、当前版本 5 GB。若额外复制当前版本做备份，还可能再占 5 GB。用新版本最终只需 5 GB 来判断磁盘余量，就会低估部署过程；日志余量和 inode 还需单独检查。数字为预算示例，不是设备实测。

把新版本放到独立目录校验后再切换指针，可以避免逐文件覆盖。但已运行进程不会因为符号链接变化就全部换成新库，仍需要停启协调、环境重载和健康检查。只有这些步骤完成后，才算整套运行状态切到了新版本。

切换版本以后，什么检查通过才算部署成功

激活是一次切换，健康是切换之后的实际行为。保留旧目录只有在恢复步骤可验证时才构成回滚能力。

动态库验证

加载目标环境后检查所有可执行文件的动态依赖，并验证运行时能够发现关键包和资源。

备份应记录来源提交、构建时间、依赖版本和校验值。只保留一个名字含 backup 的目录不构成可靠回滚。

部署验证顺序

  1. 校验架构与文件完整性。
  2. 加载环境并检查包发现。
  3. 检查动态库。
  4. 启动只读或无运动节点。
  5. 验证传感器和接口。
  6. 低风险任务测试。
  7. 确认后再删除旧版本。

部署失败时保留原正式目录，不做半覆盖。空间不足先报告可清理对象，由维护者确认后再删除旧备份。

检查项必须记录的内容
构建身份提交、编译器、sysroot、依赖锁、目标架构
产物类型SDK、应用 install 或完整集成包
空间峰值压缩包、临时解压、新旧版本、备份、日志余量
激活方式版本目录、原子指针、健康检查
完整性文件哈希、包索引、资源发现、动态库和环境前缀
回滚旧版本身份、切换步骤和验证结果

原子部署可抽象为 STAGED→VERIFIED→ACTIVATED→HEALTHY。任何阶段失败都保留旧版本；激活只切换版本指针，回滚则指回旧版本，避免再次复制整棵运行目录。
