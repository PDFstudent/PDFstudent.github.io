点云时间契约：MID-360、Airy 与首末点基准

合并两端讨论，区分包时间、逐点时间、扫描跨度和到达延迟，解释换话题无法完成雷达适配。

点云时间同步MID-360Airy

更换雷达后点云能在界面显示，是否就能直接用于激光惯性去畸变？两端讨论分别从 MID-360 与 Airy 的时间格式，以及 SDK 到 ROS 的消息转换追问这个问题。结论是：订阅成功、字段可解析和字段语义正确，是三层不同条件。重命名话题只能解决第一层中的名称匹配。

先检查信息有没有在传输中丢失

原始包、SDK 对象和 ROS 消息不是同一层

数据包经解码、标定和组帧后形成点云对象，再由适配器发布 ROS 消息。已组帧的笛卡尔点云并不是未解析的原始网络包。SDK 内存结构、PCL 点类型与 PointCloud2 也没有自动相同的布局。

PointCloud2 的 fields、字段偏移、类型、point_step、row_step、宽高与字节序共同定义布局。解析器不能只按某个本地结构体的大小强制解释所有消息。即使都叫 PointCloud2，一条消息可能有 ring 和 timestamp，另一条只有 XYZI。

丢掉逐点时间后，转换器不能无损补回来

运动去畸变需要知道每个点在扫描期间何时测得。中间对象只保留 XYZI 时，后续换消息类型不会恢复真实发射时间。按点序和固定周期估算时间需要扫描规律、点顺序及丢包假设，只能标为估计，不能冒充测量值。字段是否能通过配置启用，还取决于发布封装是否保留相关能力；底层 SDK 支持不等于最终消息支持。

MID-360 与 Airy 的时间差异应该在哪层比较

单位、分辨率和同步精度分别记录

Livox MID-360 协议规定包时间代表包内首点，时间字段采用纳秒单位，并区分未同步与外部同步的时间来源。原讨论对 Airy 解码器的调查报告包头秒与微秒部分，以及驱动按 double 秒表达逐点时间；具体发布链仍应核对版本、点类型和封装转换。Airy 官方解码实现

纳秒单位不等于纳秒级绝对精度，微秒字段也不能被直接解释成与另一雷达相差千倍的同步误差。同步性能取决于共同时间源、偏移、抖动和实际采样时间的对应关系；两台设备支持 PTP，不表示未经配置就已同步，更不表示相机自动加入了同一时基。

相对时间换算必须与真实字段单位对应

以需要相对毫秒的接口为例：

纳秒绝对时间：Δt_ms = (t_i_ns - t_ref_ns) / 1e6
秒绝对时间：  Δt_ms = (t_i_s  - t_ref_s)  * 1e3

这两式只是单位换算，不包含时钟校准。若驱动字段已经是相对时间，不能再次减去绝对帧头。原回答曾发现预处理分支直接写定换算，而不是统一使用某个 YAML 单位参数，因此应沿实际代码读取位置检查，不能只修改参数名字。

RoboSense 参数文档明确区分 use_lidar_clock 与 ts_first_point：前者选择雷达或主机时间，后者选择首点或末点作为点云时间。选择雷达时间是时间源决策，并不是同步完成的证据。

到达延迟很小，为什么仍可能整帧错位

扫描跨度与接收延迟的推导

令 t0 为首点测量时刻，t1 为末点时刻，t2 为接收记录时刻，且三者已转换到可比较的时基：

S = t1 - t0
L_end = t2 - t1
L_start = t2 - t0 = S + L_end

教学例子：扫描跨度为 80 毫秒、末点之后的发布接收耗时为 5 毫秒，使用末点帧头会看到 5 毫秒，改用首点会看到 85 毫秒。实际数据流没有因此变慢，变化的是计时起点。这些数值不是现场测量。

若算法把帧头当首点，却收到末点时间，再加上正的逐点偏移，整帧就会向后错开约一个扫描跨度。10 Hz 对应的周期约为 100 毫秒，但实际跨度仍由切帧、丢包及有效点范围决定，不能只用频率倒数代替逐点检查。

完整时间契约还包括排序与过滤

第 i 点可写成 t_i=t_ref+Δt_i。应明确参考点、偏移正负、单位、点排序和与 IMU 的重叠时间。若读取器用最后一点估计扫描结束，重排或过滤可能破坏这个假设；若用过滤后首点代替原始扫描首点，也可能改变基准。

主机接收时间与物理采样时间之间含网络、调度及缓存延迟。传感器时钟和接收者时钟还有偏差或漂移时，简单相减将混入时钟误差。低到达差值、稳定发布频率、静止点云清晰，都不足以独立证明运动去畸变正确。

从解析到融合的验收边界

逐项核对，再用运动场景验证

先确认实际消息字段、点时间范围、帧头来源、IMU 单位和外参，再检查运动期间的几何一致性。新雷达的点密度和视场变化也会影响处理负载与环境可观测性，不能把适配成功等同于精度提升。IMU 提供加速度和角速度仍需核对最终 ROS 输出单位，不应沿用旧设备的重复转换。
