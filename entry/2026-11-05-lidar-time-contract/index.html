点云时间契约：MID-360、Airy 与首末点基准

合并两端讨论，区分包时间、逐点时间、扫描跨度和到达延迟，解释换话题无法完成雷达适配。

点云时间同步MID-360Airy

更换雷达后点云能在界面显示，是否就能直接用于激光惯性去畸变？两端讨论分别从 MID-360 与 Airy 的时间格式，以及 SDK 到 ROS 的消息转换追问这个问题。结论是：订阅成功、字段可解析和字段语义正确，是三层不同条件。重命名话题只能解决第一层中的名称匹配。

先检查信息有没有在传输中丢失

原始包、SDK 对象和 ROS 消息不是同一层

数据包经解码、标定和组帧后形成点云对象，再由适配器发布 ROS 消息。已组帧的笛卡尔点云并不是未解析的原始网络包。SDK 内存结构、PCL 点类型与 PointCloud2 也没有自动相同的布局。

PointCloud2 的 fields、字段偏移、类型、point_step、row_step、宽高与字节序共同定义布局。解析器不能只按某个本地结构体的大小强制解释所有消息。即使都叫 PointCloud2，一条消息可能有 ring 和 timestamp，另一条只有 XYZI。

PointCloud2 的 data 长度还应与 row_step×height 相符；存在 ring 字段不等于二维组织成立，同一发射组的多个点时间相同也未必异常。ROS 消息定义

丢掉逐点时间后，转换器不能无损补回来

运动去畸变需要知道每个点在扫描期间何时测得。中间对象只保留 XYZI 时，后续换消息类型不会恢复真实发射时间。按点序和固定周期估算时间需要扫描规律、点顺序及丢包假设，只能标为估计，不能冒充测量值。字段是否能通过配置启用，还取决于发布封装是否保留相关能力；底层 SDK 支持不等于最终消息支持。

MID-360 与 Airy 的时间差异应该在哪层比较

单位、分辨率和同步精度分别记录

Livox MID-360 协议规定包时间代表包内首点，时间字段采用纳秒单位，并区分未同步与外部同步的时间来源。原讨论对 Airy 解码器的调查报告包头秒与微秒部分，以及驱动按 double 秒表达逐点时间；具体发布链仍应核对版本、点类型和封装转换。Airy 官方解码实现

纳秒单位不等于纳秒级绝对精度，微秒字段也不能被直接解释成与另一雷达相差千倍的同步误差。同步性能取决于共同时间源、偏移、抖动和实际采样时间的对应关系；两台设备支持 PTP，不表示未经配置就已同步，更不表示相机自动加入了同一时基。

相对时间换算必须与真实字段单位对应

以需要相对毫秒的接口为例：

纳秒绝对时间：Δt_ms = (t_i_ns - t_ref_ns) / 1e6
秒绝对时间：  Δt_ms = (t_i_s  - t_ref_s)  * 1e3

这两式只是单位换算，不包含时钟校准。若驱动字段已经是相对时间，不能再次减去绝对帧头。原回答曾发现预处理分支直接写定换算，而不是统一使用某个 YAML 单位参数，因此应沿实际代码读取位置检查，不能只修改参数名字。

RoboSense 参数文档明确区分 use_lidar_clock 与 ts_first_point：前者选择雷达或主机时间，后者选择首点或末点作为点云时间。选择雷达时间是时间源决策，并不是同步完成的证据。

到达延迟很小，为什么仍可能整帧错位

扫描跨度与接收延迟的推导

令 t0 为首点测量时刻，t1 为末点时刻，t2 为接收记录时刻，且三者已转换到可比较的时基：

S = t1 - t0
L_end = t2 - t1
L_start = t2 - t0 = S + L_end

教学例子：扫描跨度为 80 毫秒、末点之后的发布接收耗时为 5 毫秒，使用末点帧头会看到 5 毫秒，改用首点会看到 85 毫秒。实际数据流没有因此变慢，变化的是计时起点。这些数值不是现场测量。

若算法把帧头当首点，却收到末点时间，再加上正的逐点偏移，整帧就会向后错开约一个扫描跨度。10 Hz 对应的周期约为 100 毫秒，但实际跨度仍由切帧、丢包及有效点范围决定，不能只用频率倒数代替逐点检查。

完整时间契约还包括排序与过滤

第 i 点可写成 t_i=t_ref+Δt_i。应明确参考点、偏移正负、单位、点排序和与 IMU 的重叠时间。若读取器用最后一点估计扫描结束，重排或过滤可能破坏这个假设；若用过滤后首点代替原始扫描首点，也可能改变基准。

主机接收时间与物理采样时间之间含网络、调度及缓存延迟。传感器时钟和接收者时钟还有偏差或漂移时，简单相减将混入时钟误差。低到达差值、稳定发布频率、静止点云清晰，都不足以独立证明运动去畸变正确。

从解析到融合的验收边界

逐项核对，再用运动场景验证

先确认实际消息字段、点时间范围、帧头来源、IMU 单位和外参，再检查运动期间的几何一致性。新雷达的点密度和视场变化也会影响处理负载与环境可观测性，不能把适配成功等同于精度提升。IMU 提供加速度和角速度仍需核对最终 ROS 输出单位，不应沿用旧设备的重复转换。

本篇基于本机原问答及另一采集端的脱敏技术交接，后者不是主机直接读取的原文。公开协议和参数文档用于核对具体定义；本轮没有连接雷达、测同步精度或修改驱动。内部设备信息和现场测量不进入公开结论。

包内时间层级怎样对应同一参考

block、firing、channel 不是多套独立时钟

通用表达为 t_i=t_packet_ref+Δt_i。某些协议可再拆成：

t_point = t_ref + Δt_block + Δt_firing + Δt_channel

t_ref 是包参考时刻，其他项是测量块、发射组及通道相对于该参考的偏移。例如教学取值 20、6、0.4 微秒，总偏移为 26.4 微秒；这不是设备发射表。若参考对应末次测量，前面的偏移可能为负。也有协议直接查每点偏移表，并不需要上述三个独立层级。

ROS 不必为每个点调用一次 now。保留硬件包时刻与用主机收包时刻作参考，都能生成逐点字段，但绝对准确性不同。把首点选作 header 只改变帧参考，不自动修正逐点时序。点在消息中的存储顺序也未必是采样时间顺序，不能排序后就宣称修复了协议。

大时间差与小延迟为什么要分开分析

UTC、TAI 与传输链不能混为一谈

较大且近似固定的整秒偏差，可以提示检查时间尺度、纪元和偏移配置，但不能把任意整秒差都归为闰秒。需要连起源时钟、目标时钟、各自采用的时间尺度以及转换方向。LinuxPTP 的 phc2sys 中，-s 指源、-c 指接收同步的目标、-O 配置偏移；不能脱离源目标关系照抄历史常数。phc2sys 官方文档

原回答曾对现场根因作判断；本轮只核对参数含义，没有复查现场时钟。接收时刻减传感器时间还包含传输、缓存、调度及帧参考差异，不能直接称作纯时钟同步误差。尤其以首点时间比较收包时刻时，还可能包含整帧扫描持续时间。

共同主机时间仍可能标记不同事件

两个驱动都调用主机时钟，一方可能标记物理采样，另一方标记包到达或发布完成。共同时间域让数值可比较，却不会消除这两个事件之间的延迟。邻近接收时刻配对得到的差值，也不能未经分析就当作固定标定偏置。

要区分恒定偏移、长时漂移与随负载改变的抖动。静止数据能检查格式和部分时序，运动时的几何畸变还依赖扫描内偏移、姿态估计和外参。原交接中的短时统计不作为本轮动态精度验收。

软件打戳、硬件同步和设备能力的边界

协议支持不等于已经启用

软件打戳可把消息放到同一主机时间域；硬件同步还要求采样时钟或触发与公共基准建立关系。PTP、PPS 和外部触发并非同义词：PPS 提供周期边沿，绝对纪元通常仍需其他时间信息。单端完成同步，不能证明另一端驱动也保留了真实采样时刻。

应核对型号、引脚、线束、同步源、触发配置、包内时间字段和驱动处理。系统里出现 PPS 节点，不能只凭名字认定接入了物理脉冲；软件模拟源也可能暴露接口。原问答对协议能力与实际启用作了区分，未确认的硬件状态继续保留为待验证。

参数接受写入不保证运行逻辑改变

参数在初始化读取还是在动态回调处理，决定是否能热更新。可分别检查参数服务值、启动配置与实际输出时间关系；写入成功不意味着采样器已经重建。字段或组帧语义变化还可能需要实现适配。本篇不复用历史服务操作，也未重启任何传感器。

时钟对齐后，为什么还要检查机械关系

改 frame 名称不会变换数值

从 A 坐标系到 B 坐标系应执行 p_B=R_BA p_A+t_BA；仅修改 frame_id 字符串没有执行这个运算。URDF 与关节状态描述本体内部运动链，全局定位和里程计负责其他参考系关系，三者不能互相替代。

若 LiDAR 与 IMU 跨越活动关节，T_LI(t) 随时间变化。依赖固定外参的估计器，不会仅因为 TF 可查询就自动正确处理这种变化。还须核对真实机械刚性、关节采样时间、坐标轴、单位和估计器假设。

本文来自采集端脱敏交接，发布端未直接读取该设备原始会话，也没有重做硬件或融合实验。结论是分别验收数据布局、相对时序、绝对时钟、几何契约及动态结果；后者不能由前几项配置检查自动推出。
